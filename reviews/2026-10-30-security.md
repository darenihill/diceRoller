# Security review, first pass (2026-10-30)

Dice Roller is a public, static site (customdiceroller.com) with no accounts,
no server and no secrets. Everything a person makes lives in their own
browser storage. So the threats are about what comes in from outside:
- share links;
- backup files;
- landing pages;
- what goes out to Google Analytics.

## Where data crosses in and out

| Way in or out | Who controls it | Guard |
|---|---|---|
| Share link `#share=…&name=…` | Anyone who sends a link | `readShareLink` → `sanitizeDiceList` (50 dice, 1000 faces, 100 custom faces, 60 characters, hex colours only); name cut to the name limit; React escapes all text |
| Backup file (Import) | Anyone who hands someone a file | Dice lists and pictures sanitised; **roll history and theme were not** (fixed below) |
| Landing pages `data-start` and about text | Us, at build time | Built from `landing/pages.mjs`; the about text is our own HTML |
| Face pictures | The person, from their own photos | Only small `data:image/png|jpeg|webp` base64, 200 at most, 60 KB each |
| Google Analytics | Sent out when telemetry is on (on by default; the app has a switch to turn it off) | Only built-in game names are sent, never a save's name. **The page address could carry a share link** (fixed below) |
| Buy Me a Coffee and Ideas form links | Outside sites | **Opened with access back to our tab** (fixed below) |

## STRIDE walk

| Kind | Finding | Verdict |
|---|---|---|
| Spoofing | No accounts and nothing to sign in to. A share link can name its set anything, but it only shows as plain text. | Nothing to fix |
| Tampering | A hand-edited backup could store any roll history. One bad entry, e.g. `{}`, crashed the app every time History was opened, until the site data was cleared. Its theme was also stored as-is and put on the page's class list. | **Fixed:** history is checked on load; theme must be one of the four shipped |
| Repudiation | Nothing is shared between people, so there is nothing to deny. | Nothing to fix |
| Information leak | Google Analytics' page view used the full address. A share link's `#` part holds the dice, face text and set name. | **Fixed:** every page sends only the address before `#` |
| Information leak | Outside links opened with `window.open(url, '_blank')`, so the new tab could reach back and change ours. | **Fixed:** `noopener,noreferrer` |
| Denial of service | Share links: the dice and face limits hold after decompressing. The worst a huge link does is a slow first load for the person who taps it, and the URL length limits it. | Accepted |
| Denial of service | The History screen crash from a bad backup (above). | **Fixed** |
| Elevated access | No server, no roles. The only HTML injected is our own landing text. No `eval`. | Nothing to fix |

## Checked and fine

- No secrets in the code. The analytics ID is public by design.
- `npm audit --omit=dev`: 0 issues in what ships. The dev-only tools (vitest's mocker and brace-expansion) have advisories, but they never reach the site. They're left for the dependency lens, because a package change needs a second agent to vouch for it.
- The service worker only caches our own files and Google Fonts, and skips anything that isn't a GET.
- Pull request 63 (backup keeps all settings) rewrites Import. These fixes guard at load time instead, so they protect both the old and the new Import and don't clash with it.

## Not done, worth a later look

- A Content-Security-Policy. The site is on GitHub Pages, so it would be a `<meta>` tag. The inline scripts would need hashes, or the analytics snippet would have to move to a file. A mistake there breaks the public site, so it goes to the Desk as an idea rather than a quiet fix.

## Tests

`src/test/security.test.tsx`:
- malformed history is dropped;
- the History screen opens with a bad backup;
- an unknown theme falls back to dark;
- every page's analytics call leaves out the `#` part.
